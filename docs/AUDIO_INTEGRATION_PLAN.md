# CubeKorean 韩语音频接入方案（审核稿）

- 状态：已确认，P17-A首批20词已生成，等待人工审音
- 日期：2026-09-10
- 目标版本：P17
- 推荐方案：Azure Speech F0 离线批量生成 + Sites 静态音频托管

## 1. 背景与结论

当前发音依赖浏览器 Web Speech API。实际测试中，MacBook 上的 Chrome 和 Safari 均出现无声，且可用声音、音质和播放行为受操作系统及浏览器影响，无法作为拼写训练的可靠主链路。

本方案不在用户练习时调用外部语音接口，而是在发布课程前使用 Azure Speech 批量生成固定 MP3。网页只播放随站点发布的静态音频；网络接口、密钥和免费额度均不进入用户练习链路。

```text
课程词汇（稳定 wordId + 韩文）
  ↓ 本地生成脚本，仅在内容发布前运行
Azure Speech REST API
  ↓
public/audio/ko/{wordId}.mp3 + 音频清单
  ↓ 随 Sites 发布
浏览器 HTMLAudioElement 播放
  ↓ 资源缺失时
Web Speech 备用 → 明确的不可用提示
```

## 2. 为什么选择静态 MP3

| 维度 | 静态 MP3 | 浏览器 Web Speech | 练习时实时调用 Azure |
|---|---|---|---|
| Chrome / Safari 一致性 | 高 | 低 | 中高 |
| 用户练习时依赖第三方接口 | 否 | 依赖系统实现 | 是 |
| 密钥暴露风险 | 无前端密钥 | 无 | 直接前端调用会暴露密钥 |
| 超额收费风险 | 只在生成阶段可控 | 无 | 随使用量增长 |
| 离线或弱网复用 | 可被浏览器缓存 | 不确定 | 差 |
| 发布前人工审音 | 可以 | 不可以固定版本 | 可以，但难以锁定结果 |

该选择继续保持“课程数据、拼写规则、学习会话、页面展示职责分离”，也不引入账号、数据库、R2或运行时服务端状态。

## 3. 供应商和声音

首选 Azure Speech 标准神经语音：

- 默认女声：`ko-KR-SunHiNeural`；
- 备选男声：`ko-KR-InJoonNeural`；
- 区域优先选择创建 Speech F0 资源时实际可用的区域，例如 `koreacentral`；
- 输出格式拟使用 `audio-24khz-48kbitrate-mono-mp3`，在清晰度和静态体积之间取平衡；正式实现前用20词样本确认该格式仍受当前接口支持。

Azure 官方文档确认 REST TTS 需要与资源匹配的区域端点和资源密钥，并通过 SSML 指定语言及声音。韩语当前提供上述声音及其他 `ko-KR` 声音。

参考资料：

- [Azure Speech 定价](https://azure.microsoft.com/en-us/pricing/details/speech/)
- [Azure Speech 韩语声音支持](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support)
- [Azure Text to Speech REST API](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/rest-text-to-speech)

免费额度属于供应商当前政策，不写入产品承诺。生成前应在 Azure 门户确认资源为 F0，并设置预算或告警；脚本默认跳过已生成且内容未变化的词，避免重复消耗额度。

## 4. 文件与数据设计

### 4.1 静态文件

```text
public/audio/ko/
├── daily-food-01-001.mp3
├── daily-food-01-002.mp3
└── manifest.json
```

文件名使用稳定 `wordId`，不直接使用韩文，避免空格、标点、同形词和URL编码问题。

### 4.2 音频清单

`manifest.json` 至少记录：

```json
{
  "version": 1,
  "voice": "ko-KR-SunHiNeural",
  "format": "audio-24khz-48kbitrate-mono-mp3",
  "items": {
    "daily-food-01-001": {
      "text": "커피",
      "sourceHash": "内容与声音配置摘要",
      "path": "/audio/ko/daily-food-01-001.mp3"
    }
  }
}
```

课程词条仍是事实来源，清单仅描述已生成资源。韩文、声音、语速或输出格式变化时，`sourceHash` 变化，对应文件才需要重新生成。

### 4.3 发音例外

单独词汇可能存在同形异音、数字、英文缩写、空格短语和语境不足。实现时增加小型发音覆盖表，只保存确有审音依据的 SSML 文本或读法，不把发音规则塞进课程展示数据。

## 5. 播放行为

- 用户点击发音按钮属于明确播放手势，使用同一个 `HTMLAudioElement` 实例播放；
- 自动发音只在用户已经开始练习后触发，若浏览器阻止自动播放，不影响输入并提示点击发音按钮；
- 切换单词前停止上一段，避免多段音频叠加；
- 当前词播放时预加载下一词，但不一次性预载整个关卡；
- 静态音频加载或解码失败时尝试一次现有 Web Speech 备用；
- 两种方式均失败时显示“当前发音不可用，可继续拼写”，不阻断答题；
- 播放状态应包含加载、播放、失败，重复点击不会并发叠音。

## 6. 密钥与安全边界

- `AZURE_SPEECH_KEY` 和 `AZURE_SPEECH_REGION` 只提供给本地生成命令；
- 密钥不得写入源码、`.env.example` 的真实值、Git历史、浏览器包或日志；
- 前端不请求 Azure，不新增公开代理接口；
- SSML 文本只来自仓库内已校验课程和发音覆盖表，不接受用户输入；
- 生成脚本对HTTP错误、限流和空响应明确失败，不用空文件覆盖已有音频。

## 7. 分阶段实施

### P17-A：20词试音

1. 新增生成脚本、音频清单和静态音频播放器适配器；
2. 选择“日常饮食”第1小关20词生成样本；
3. 在Mac Chrome和Safari测试手动播放、自动播放、连续切词和失败回退；
4. 人工审核自然度、重音、停顿和音量，确认默认声音；
5. 记录20个文件的实际总大小，据此估算2000词发布体积。

当前结果：20个文件均已生成并识别为24kHz、48kbps、单声道MP3，总计200,592字节；本地预览返回 `audio/mpeg`，自动播放后未出现页面错误，仍需由用户实际听感确认声音。

### P17-B：全量生成

1. 对100关×20词生成音频；
2. 校验每个有效 `wordId` 恰有一个可解码文件，且不存在孤立文件；
3. 对全部文件做自动完整性检查，对每个主题抽样人工审音；
4. 对异常词添加发音覆盖并重新生成；
5. 完成桌面和手机主路径回归后发布。

## 8. 测试与验收标准

### 自动测试

- 课程词条到音频路径的稳定映射；
- 清单缺项、重复项、内容摘要过期和孤立音频检测；
- 播放成功、资源失败、Web Speech备用失败和快速切词；
- 音频失败不改变拼写输入、错误次数、分组进度或错词记录；
- 运行现有相关测试、`npm run lint` 和 `npm run build`。

### 人工验收

- Mac Chrome、Mac Safari各完整练习一组5词；
- 手动发音每次可听见，连续快速点击不叠音；
- 开启自动发音后进入听写阶段能播放；若被浏览器策略拦截，界面反馈明确；
- `커피` 等20词样本无明显错读、截断、爆音或音量突变；
- 模拟一个MP3缺失时仍可输入、提交和完成关卡。

### P17-B上线门槛

- 2000个有效词条的音频覆盖率为100%；
- 自动完整性校验为0错误；
- 每个主题至少抽听20词，所有发现的问题已关闭或进入明确的阻塞清单；
- 不存在进入浏览器构建产物的Azure密钥。

## 9. 回滚方案

播放器适配器保留现有 Web Speech 实现。若静态音频引发发布体积、缓存或兼容问题，可将播放优先级切回 Web Speech 并移除静态资源引用，不影响课程、拼写、进度和错词数据。P17-A只覆盖一个小关，回滚范围可控。
